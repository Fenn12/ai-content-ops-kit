# Skill 编写规范

一份 Skill 的价值，不在于它写得多长，而在于**别人拿到它能不能稳定复现你的产出**。

---

## 一句话判据

> 如果一个新人读完你的 Skill、不改一个字就能产出你要的水准，这个 Skill 就是合格的。
> 如果他还得回来问你「这里是什么意思」，说明你写的是笔记，不是 Skill。

---

## 什么该写进 Skill

| 类型 | 例子 | 原因 |
|---|---|---|
| **判定标准** | 「什么算合格」的具体阈值 | 这是最难传递、也最值钱的部分 |
| **禁用清单** | 合规红线、绝对化用语、竞品名 | 越明确越省事，模糊就会漏 |
| **输出格式** | JSON schema、字段含义 | 决定下游能不能自动化 |
| **处理分支** | 输入不全时追问，而不是猜 | 避免模型自由发挥 |
| **失败样例** | 「这种写法不要」+ 反例 | 反例比正例更能定位问题 |

## 什么不该写进 Skill

| 类型 | 为什么 |
|---|---|
| **具体某个产品的文案** | 那是一次性产出，不是能力 |
| **「要写得好」「要有感染力」** | 无法判定，等于没写 |
| **过长的背景介绍** | Skill 不是项目报告，背景放在 README |
| **会频繁变动的信息** | 放配置或参数，别硬编码进 Skill |
| **公司内部数据、真实投放策略** | 合规风险；Skill 应可脱敏复用 |

---

## 四个必备模块

### 1. 元信息 + 变更记录
```yaml
name: xxx
version: 3.2
changelog:
  - v3.2 改了什么，为什么
```
**变更记录是面试时最有说服力的部分**——它证明你真的迭代过，而不是一次写完。

### 2. 适用边界
明确写「不适用什么」。这比写「适用什么」更能体现判断力。

### 3. 输入契约
字段、必填与否、输入不全时的处理策略。
**关键：把「猜」这个动作显式禁掉。** 模型最危险的行为就是自动补全出看似合理但脱离真实的输入。

### 4. 自检清单
输出前必须跑一遍的可判定项。任何一项不过，重写而不是输出。

## 版本迭代的写法

每次改 Skill，记录三件事：

```markdown
### v3.2（2026-10-20）
**触发**：评测集第 14 条（卖点模糊）通过率只有 40%
**改动**：新增「输入不全返回追问清单」规则
**结果**：该条通过率 40% → 85%，整体 68% → 79%
**副作用**：生成轮次增加约 1.2 轮，平均耗时 +8 秒
```

**一定要写副作用。** 只写提升不写代价的迭代记录，一眼就能看出是包装过的。

## 常见错误

1. **把 prompt 当 Skill。** Prompt 是一次性指令，Skill 是可复用规范。前者求结果，后者求稳定。
2. **只写正例不写反例。** 模型不知道什么是「错」，就一定会犯。
3. **没有评测就宣布优化。** 「我感觉好了」不是证据，跑评测集才是。
4. **无止境加规则。** 规则加太多会互相冲突，最后模型不知道听谁的。定期合并与删除。
5. **让 AI 做终审。** 合规、调性、事实核查，这三件事永远留给人。
